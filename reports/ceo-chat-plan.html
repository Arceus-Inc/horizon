Horizon · Theme D · design plan

The CEO — a chattable executive employee

One identity with two faces: a conversation you talk to about the entire company, and a real employee that runs high-level beats — governance, decisions, reviews. It is informative (answers grounded in live company state), directive (drafts and drives decisions, gated by your approval), and remembering (a persistent memory of every conversation, decision, and directive).

💬 Chat surface — ask it anything about the company 🧑‍✈️ Executive employee — runs governance & decision beats 🧠 Memory store — remembers, recalls, and decays

The CEO sits at the very top of the Decision → Goal → Task spine. Below it, horizon decomposes decisions, chorus runs the org, dream completes tasks. The CEO is the human's single point of contact with all of it — and, uniquely, it can also act as a bounded employee when the work itself is executive.

The dual nature

Face 1 · Chat

You talk to it

A live conversation. Ask about strategy, status, risks, people, spend, a specific decision or goal — it answers from the real company state, cites its sources, and can act on your instruction (draft a decision, approve a proposal, re-prioritise) behind a confirm gate.

Informative + directive, always grounded, never auto-applying a write.

Face 2 · Employee

It runs beats

The CEO is a real chorus employee (role="ceo") that can be handed very high-level tasks — a governance audit, a quarterly decision review, adjudicating the funnel's proposals, a risk assessment — and runs them as bounded beats with executive-grade tools.

The same identity, memory, and context back both the chat and the beat.

Informative — answers about the entire company

Every answer is grounded in live state and cites where it came from (a goal id, a task verdict, a ledger row, a memory). No vibes — evidence.

Gated writes

What it can do — always confirmed

Draft & seed a decision · approve/reject a funnel proposal · re-prioritise or archive a goal · open a governance beat · record a standing directive.

Each produces a preview diff + evidence refs; the write happens only on your confirm.

Escalation

When it acts on its own

Within standing directives you've pre-approved (e.g. “auto-approve proposals above 0.8 confidence with ≥3 evidence refs”), it may act and report after — every autonomous action still writes an auditable record.

You set the leash; it stays inside it.

Every write tool returns a preview (a diff + evidence), never an immediate mutation. The confirm step is the single door from “the CEO suggested” to “the company changed” — the same proposal-only invariant the generation funnel already enforces.

Memory — informative, directive, and persistent

The CEO's memory is what makes it feel like the same executive across sessions. Four layers, each retrievable by the assembler and each with its own decay.

Conversation
Rolling chat history + periodic summaries. “What did we discuss last week?” — decays fast; summarized, not verbatim, after N turns.
Decision log
Every decision + its rationale, who approved it, and how it turned out. “Why did we choose mid-market?” — long-lived; the audit trail of strategy.
Directives
Standing instructions & preferences you've given (“always prioritise the deliverable over analysis polish”). — persistent; shapes future decompositions + auto-approvals.
Org facts
Durable truths about the company — product, market position, constraints, people. — slow-changing; the CEO's world model.

How it writes

After a turn, the CEO distills what's worth keeping — a decision made, a directive given, a fact learned — into the right layer (a write_memory gated for directives, automatic for the decision log).

How it recalls

The assembler retrieves by relevance to the current question (semantic + recency + importance), so a passing mention months ago resurfaces exactly when it matters — and stale, superseded memories fade.

The CEO as an employee — executive beats

Uniquely, the CEO can be handed a task and run it as a bounded beat — but only work that is genuinely executive. It shares the chat's context, tools, and memory, so a beat is just “the CEO thinking hard, unattended, and writing back a directive-grade result.”

Governance

Governance audit

Scan the whole tree + ledger for drift, stale goals, runaway cost, blocked work; produce a findings memo + a set of proposed corrections (gated).

Decision

Decision authoring

Given a mission + evidence, author a full decision (or adjudicate the funnel's proposals) with rationale and risks — the top of the spine, written by the top of the org.

Review

Quarterly / risk review

Roll up the sprint: what shipped, what it cost, what's at risk, what to change next quarter — an executive report a human board could read.

Guardrail: the CEO beat's outputs are still gated. A governance audit proposes corrections; a human (or a standing directive) confirms them. The CEO can think autonomously; it can't unilaterally rewrite the company.

Build plan (incremental)

D1
Context assembler + read-only chat. Assemble the tree/ledger/proposals/ops into a bounded context; a chat that answers questions with citations. No writes yet. Proves: the CEO is informative and grounded.
D2
Memory store. The four layers + write/recall; the assembler pulls relevant memory into each turn. Proves: it remembers across sessions.
D3
Directive chat (confirm-to-write). The gated write tools (draft/seed decision, approve proposal, set priority, archive goal, record directive) with preview diffs. Proves: it's directive, safely.
D4
CEO as employee. The role="ceo" chorus beat: governance audit + decision review, sharing the chat's context/tools/memory. Proves: it can beat on executive work.
D5
Standing directives + bounded autonomy. Pre-approved rules let it act and report-after; a capstone: a signal → CEO audit → proposed corrections → your one-tap approval → the org re-aims. Proves: the whole executive loop.

Open questions (defaults to decide)

Memory backend

Start file-backed + keyword/recency recall (like the existing stores); add embeddings for semantic recall when the decision log grows. Default: files first.

Autonomy leash

How much can standing directives pre-authorise? Default: read + propose freely; writes need confirm unless a directive explicitly pre-approves a narrow class.

Chat ↔ beat identity

One CEO identity backing both, or a “chat CEO” that dispatches beats to itself? Default: one identity, one memory; a beat is an unattended turn.

Context budget

How much company state per turn? Default: rank by recency × relevance × importance, trim to a fixed token budget; the assembler owns it.
