- **IaC/config:** Terraform/OpenTofu, Pulumi, CloudFormation; Helm/Kustomize
- **Observability:** Datadog, New Relic, Grafana/Prometheus, OpenTelemetry
- **IDP / Dev Portal / Workflow:** Backstage (or evaluating), internal tooling sprawl, self-serve needs
- **Security tooling (signals):** Snyk, Wiz, Prisma, OPA/Gatekeeper/Kyverno

# Mid-market Platform/DevEx Inbound Qualification Checklist & Playbook

**Purpose:** Qualify inbound leads for a mid-market Platform Engineering / Developer Experience (DevEx) product consistently. This is a single, end-to-end artifact: intake requirements → checklist → scoring → disqualifiers → routing actions → discovery script → objection handling → persona variations.

---

## ICP (Ideal Customer Profile)

### Mid-market bounds (must be true)
- **Employee range:** **200–2,000** employees (primary sweet spot: 300–1,200)
- **Engineering org size (signal):** ~**40–400** engineers (or equivalent software builders)
- **Delivery model:** ships software continuously (SaaS, digital product, platform-enabled enterprise line-of-business)

### Target buyer / champion titles
Primary economic buyer / sponsor (varies by org):
- VP Engineering
- Head/Director of Platform Engineering
- Head/Director of Developer Experience / Developer Productivity
- CTO (mid-market)

Primary day-to-day champion / evaluator:
- Platform Engineering Manager
- Staff/Principal Engineer (Platform)
- DevEx / Developer Productivity lead
- SRE/Infra Manager (when Platform reports into Infra)

### Target technical environment signals (examples)
Look for **at least 3** of the following in the lead’s stack, job posts, website, docs, or conversation:
- Cloud: AWS / GCP / Azure; multi-account/subscription setup
- Kubernetes / container platforms (EKS/GKE/AKS, OpenShift)
- Infrastructure as Code: Terraform / Pulumi / CloudFormation
- CI/CD: GitHub Actions, GitLab CI, CircleCI, Jenkins, ArgoCD
- Observability: Datadog, New Relic, Grafana, OpenTelemetry
- Internal Developer Platform (IDP) components: service catalog, golden paths, templates, developer portal
- Security/compliance needs: SOC 2, ISO 27001, HIPAA, PCI (or customer-driven security reviews)

---

## Intake data requirements (capture fields + mandatory flags)

**Mandatory (must capture before scoring/routing):**
1. **Company name**
2. **Employee count** (or range)
3. **Engineering size** (estimate acceptable)
4. **Primary contact title + function** (e.g., Platform, DevEx, Eng Mgmt)
5. **Current stack** (at least: cloud + CI/CD + runtime)
6. **Primary pain** (free text + choose category)
7. **Timeline** (e.g., “this quarter”, “6–12 months”, “just researching”)
8. **Authority / buying role** (economic buyer, influencer, evaluator)

**Strongly recommended (capture if possible):**
9. **Budget range** (or “unknown”)
10. **Security/compliance requirements** (SOC2, SSO, data residency)
11. **Integration constraints** (IdP/SCIM, VCS, ticketing, etc.)
12. **Success metric** they care about (deploy frequency, lead time, incident rate, onboarding time)

---

## Qualification checklist (numbered questions + pass/fail guidance)

Answer **Yes/No** and note the **evidence source** (form field, call notes, website, job postings, technical doc, etc.).

1. **Is the company within 200–2,000 employees?**
   - Pass: confirmed within range (or strong evidence).
   - Fail: <200 or >2,000 (unless exception approved).
   - Evidence: LinkedIn, Clearbit, customer-provided.

2. **Is there a meaningful engineering organization (≈40+ engineers) building/operating software?**
   - Pass: 40+ engineers or equivalent, multiple teams/services.
   - Fail: very small dev team, mostly outsourced, or non-software org.
   - Evidence: org chart, hiring pages, conversation.

3. **Is the lead’s function aligned to Platform/DevEx outcomes?**
   - Pass: Platform/DevEx/Engineering leadership, SRE/Infra leader owning dev workflows.
   - Fail: unrelated function (e.g., pure marketing ops) with no engineering mandate.
   - Evidence: title, responsibilities, call.

4. **Do they have a current developer workflow/platform complexity signal (cloud + CI/CD + runtime)?**
   - Pass: cloud + CI/CD + containers/K8s or significant microservices/platform sprawl.
   - Fail: single monolith + manual deploys + minimal tooling (unless they are actively modernizing).
   - Evidence: stack disclosure, public repos/docs, call.

5. **Is there an explicit pain that a Platform/DevEx solution addresses?**
   - Pass: pain mapped to developer productivity / reliability / standardization.
   - Fail: vague interest (“curious”), no clear pain.
   - Evidence: form text, discovery.

6. **Is the pain acute enough to justify near-term action?**
   - Pass: deadline, incidents, growth, compliance, cost pressure, platform initiative this/next quarter.
   - Fail: “someday” with no sponsor or initiative.
   - Evidence: timeline, triggers.
